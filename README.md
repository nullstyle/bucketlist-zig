# bucketlist-zig

Typed Zig databases with deterministic BucketList commitments, designed to pair
with `slcp-zig`. Applications define tables, keys, and record values; the library
owns canonical encoding, atomic batches, immutable buckets, merge scheduling,
and exact checkpoint recovery.

**Status: implemented, Experimental `0.1.0-dev`.** Stellar Core is the structural
reference. Stellar ledger types, XDR, and hash compatibility are outside scope.

The portable `bucketlist` module provides:

- `Database(Schema)` with explicit numeric table IDs and bounded typed codecs.
- Allocation-free reads, atomic multi-table prepare/commit, and pinned read views.
- Eleven factor-four levels with delayed promotion and safe tombstone retention.
- SHA-256 commitments that bind the schema, sequence, list, and pending merges.
- Strict checkpoint import checked against an independently trusted digest.

The native `bucketlist-store` module provides durable content-addressed blobs,
verified reads, atomic manifest publication, explicit reachability collection,
and bounded-memory file merges. The `bucketlist-checkpoints` module builds on
that store: it publishes typed read views with application recovery metadata,
shares unchanged bucket files, restores exact database state, and collects
unreferenced files while retaining selected historical checkpoints. The
portable database engine operates in memory.

The native `bucketlist-disk` module executes the same typed batches against
files, keeping only bucket identities in its frontier. It adds authenticated
linear reads, pinned read views, parallel streaming merges, and atomic durable
publication. `Host(Schema)` runs that work on a dedicated thread behind a bounded
queue with explicit `Backpressure`; accepted and durable advances are distinct.
See the [disk and host contract](docs/disk.md).

## Use

The [two-table directory example](examples/directory/main.zig) is compiled and
executed by the normal test gate. Its schema looks like this:

```zig
const Schema = struct {
    pub const namespace = "example.directory";
    pub const version: u32 = 1;
    pub const tables = .{
        .accounts = bucketlist.Table(1, u64, struct { balance: u64 }),
        .names = bucketlist.Table(2, bucketlist.Bytes(32), u64),
    };
};
const Directory = bucketlist.Database(Schema);
```

Create the database with `Directory.init(gpa)`, open a batch with
`try db.batch(gpa)`, put/delete typed records, prepare the next contiguous
advance, then commit it. Deinitialize the database, batches, prepared results,
and read views. Preparation does all allocating work; commit publishes without
allocation. The allocator used by preparation must outlive the resulting state
and retained views.

Batch staging uses an identity index for efficient repeated changes; committed
records still follow the specified canonical ordering. Native checkpoints borrow
bucket frames during save and restore one bucket at a time, avoiding a second
full serialized checkpoint in memory. See [measurements](docs/performance.md).

A standalone consumer [build](examples/directory/build.zig) imports
`dependency.module("bucketlist")`. The package has no external dependencies.
For native storage, also import `dependency.module("bucketlist-store")` and
provide `std.Io` explicitly.

For checkpoint management, import `dependency.module("bucketlist-checkpoints")`
and instantiate `Checkpoints(Directory)`. The
[persistent directory example](examples/persistent-directory/main.zig) shows
publication, close/reopen, exact replay, and retention. See the
[checkpoint contract](docs/checkpoints.md) for ownership and trust requirements.

For file-backed execution, import `dependency.module("bucketlist-disk")`.
The [disk directory example](examples/disk-directory/main.zig) stages ordinary
`Host.Batch` values, submits them without filesystem I/O, waits for durable
publication, and reopens with an authenticated reference. Native disk commit
performs I/O and can fail; a publication error requires reopening to resolve
its durable outcome. Allocators and `std.Io` must support the worker threads.

## Development

```sh
mise trust mise.toml
mise install
mise exec -- just doctor
mise exec -- just test
mise exec -- just wasm-diff
mise exec -- just preflight
```

`mise.toml` is the exact compiler/tool pin. Zig matches the inspected SLCP
revision; use `mise exec -- ...` to avoid another compiler manager taking PATH
precedence. Ordinary library consumers do not need the development tools.

Other checks:

- `just vectors-check` verifies fixtures generated by an independent Python model.
- `just vectors` explicitly regenerates those fixtures.
- `just fuzz-smoke` runs the seeded parser cases and the fixed guided corpus
  included in ordinary tests.
- `just fuzz-portable 100000 1` and `just fuzz-native 10000 1` run longer
  deterministic campaigns; see [coverage and replay](docs/fuzzing.md).
- `just guided-fuzz 100000 1` runs a bounded LLVM coverage-guided campaign
  behind a fail-closed wrapper with exact input replay; `just
  guided-self-test` proves that wrapper on a deliberate synthetic failure.
- `zig build bench -Doptimize=ReleaseFast` measures real updates and checkpoints.
- `zig build scalability -Doptimize=ReleaseFast -- /absolute/fresh/store/path 3`
  measures larger batches and native checkpoint allocator peaks.
- `just disk-bench /absolute/fresh/store/path 64` measures disk workloads,
  allocation peaks, and verified file traffic with one and two merge workers.
- `zig build check-api` checks the Experimental interface snapshot.
- `just package-preflight` tests an extracted archive and standalone consumer.
- `just persistent-example-smoke` exercises native checkpoint recovery.
- `just disk-example-smoke` exercises bounded background publication and disk recovery.
- `just slcp-disk-smoke` exercises disk delivery, backpressure, journal replay,
  and quorum recovery using three real SLCP processes.
- `just slcp-smoke` runs the isolated companion integration; see its
  [instructions](examples/slcp-directory/README.md).
- `just core-oracle` compares original pinned Core schedule functions with
  the fixtures; see [oracle provenance](docs/oracle.md).
- `just linux-check` executes the native tests in a disposable Docker container.

No ordinary build/test needs a sibling repository. Optional reference and SLCP
checks materialize immutable source snapshots under this repo's `.zig-cache`;
they do not build or modify a sibling working tree.

## Commitments and recovery

A BucketList root commits to the retained bucket representation and can depend
on update history. Equal visible records do not guarantee equal roots. Empty
batches still advance the schedule. Reinserted logical exports start new
histories; checkpoints resume existing histories exactly.

Use the complete `Commitment.digest` for database authentication. The list root
alone omits pending merges and the sequence. `restore` needs a trusted expected
digest; a hash read from the same untrusted file is not an independent trust
anchor. The library does not supply validator certificates or membership proofs.

## Pairing with SLCP

The [SLCP directory example](examples/slcp-directory/README.md) agrees on bounded
application values, applies them through `OwnedAppNode`, and binds database
commitments into application headers. Snapshot recovery also preserves the
exact previous consensus command.

`OwnedAppNode.apply` permits allocation failure but not file errors. Database
updates run there; host storage publication runs outside it. The example uses
a pinned Experimental SLCP interface, and does not change the consensus engine
or the existing registry's format.

The [disk SLCP host](examples/slcp-disk/README.md) uses the raw delivery hook
for bounded admission and explicitly acknowledges durable publication to keep
SLCP journal retention behind the recoverable database frontier. It preserves exact command metadata with each durable
database frontier and recovers a journaled suffix after backpressure or process
termination. Its blind-write command model requires no database I/O inside
consensus callbacks; applications with state-dependent validation need their
own bounded validation state or a suitable preparation stage.
